## activities
`src/domain/activities.fnl`

### `M.all []`

> The full content registry as a fresh shallow-copied sequence.
> Domain:  (none)
> Returns: [ActivityDef] -- a new sequence so callers cannot mutate the
> module's registry (entries are shared by reference, read-only).
> Errors:  (none).

### `M.by-id [id]`

> The ActivityDef whose :id matches, or nil.
> Domain:  id : string -- the stable activity key (e.g. :karazhan)
> Returns: ActivityDef | nil
> Errors:  (none).

### `M.by-type [type]`

> Every ActivityDef of the given content type, as a fresh sequence.
> Domain:  type : enum -- :raid :heroic :daily :weekly-quest :rep-hub
> Returns: [ActivityDef] -- a new sequence (possibly empty)
> Errors:  (none).

### `M.requirements-met? [activity player]`

> True iff the player meets every prerequisite of the activity.
> Checks, in order: level >= min-level, the optional attunement is owned, and
> the optional reputation gate is satisfied (a missing faction counts as
> :neutral). Pure predicate -- reads player state, mutates nothing.
> Domain:  activity : ActivityDef (schemas.ActivityDef; validated)
> player   : Player (schemas.Player); :level integer,
> :attunements set {key true}, :reputations {faction std}
> Returns: boolean
> Errors:  if the ActivityDef shape is invalid, or player.level is not a number.

### `M.available? [activity player ?lockout now]`

> True iff the activity is doable right now for this player.
> Gates first on prerequisites (requirements-met?); then on the lockout: no
> saved lockout or an already-reset one means open, otherwise availability
> depends on the reset cadence -- a :weekly/:daily instance is open only while
> bosses remain, a :none-reset activity is never locked out. The module never
> fetches a lockout (purity); the caller pairs the right LockoutView by id.
> Domain:  activity : ActivityDef (schemas.ActivityDef; validated)
> player   : Player (schemas.Player)
> ?lockout : LockoutView | nil -- the matching saved lockout, if any
> now      : integer -- current server time in seconds
> Returns: boolean
> Errors:  if the ActivityDef shape is invalid, or now is not a number.

## drop-chance
`src/domain/drop-chance.fnl`

### `M.at-least-one [p n]`

> Probability of at least one drop in n runs given per-run probability p.
> Domain: 0 <= p <= 1, n >= 0.
> Returns: P in [0, 1].

### `M.exactly-k [n k p]`

> Binomial probability: exactly k drops in n runs at rate p.
> Domain: 0 <= p <= 1, 0 <= k <= n, n >= 0.
> Returns: P in [0, 1].

### `M.expected-runs [p]`

> Expected number of runs until first drop (geometric distribution).
> Returns: math.huge if p = 0, otherwise 1/p.

### `M.effective-rate [p competitors]`

> Adjust drop rate p for ML competition. competitors >= 1 includes self.
> E.g. 4 casters compete on a caster trinket -> effective = p/4.

### `M.bayesian-luck [observed-drops observed-runs base-p ?prior]`

> Bayesian posterior given observed history.
> Prior: Beta(alpha, beta), default (1, 1) = uniform.
> Returns table {:posterior-mean :posterior-variance :luck-z :n}.
> :luck-z is a z-like score: (posterior-mean - base-p) / sqrt(variance).
> Positive z = luckier than expected, negative = unluckier.

### `M.make-rng [seed]`

> Deterministic [0,1) generator from an integer seed (Park-Miller MINSTD).
> Domain code never calls math.random -- a caller seeds this so a Monte Carlo
> projection is reproducible (same seed -> same stream). Overflow-safe in WoW's
> Lua 5.1 doubles: state*16807 < 2^53, so the modulus is exact.
> Domain:  seed : integer (any; normalised into the MINSTD range [1, m-1]).
> Returns: fn [] -> number in [0, 1).

### `M.coupon-collector-mc [items n-runs n-sims rng]`

> Monte Carlo simulation of coupon collector: how many slots filled after n-runs.
> items: sequence of {:slot kw :p number} entries.
> rng: deterministic RNG seeded by caller (do NOT use math.random directly here;
> purity requires injected randomness).
> Returns: {:p10 :p50 :p90} as fractions of items filled.

## goals
`src/domain/goals.fnl`

### `M.normalize [?persisted]`

> Coerce a possibly-nil / possibly-corrupt persisted list into valid GoalDefs.
> User-authored data: invalid entries are DROPPED, never an error -- a corrupt
> SavedVariables row must not take the planner down.
> Domain:  ?persisted : table | nil -- db.char.goals
> Returns: [GoalDef] -- fresh, possibly empty.

### `M.to-db [goals]`

> A fresh plain copy of the goal list for SavedVariables, so the persisted
> table never aliases the live session copy.
> Domain:  goals : [GoalDef]
> Returns: [GoalDef] (plain data)

### `M.progress [goal inputs]`

> Current progress toward a goal, read from plan-time holdings.
> Domain:  goal   : GoalDef
> inputs : {:money ?int :badge-count ?int :owned-items ?{id true}
> :standings ?{faction-kw standing-kw}
> :chain-fractions ?{chain-id number}}
> Returns: number >= 0 in the goal's own unit (copper / badges / 0|1 owned /
> standing index 1..8 / chain fraction 0..1).

### `M.runs-before-reset [adef ?now ?reset-at]`

> Planned clears of one activity left before the weekly reset.
> The deadline-aware replacement for a flat runs-per-reset table (OQ-11): a
> :daily activity offers one run per remaining day (clamped 1..7) when both
> timestamps are known, else the casual 4-nights-a-week default; :weekly and
> :none offer a single clear. Used by route scoring and the projections so
> both shrink together as the reset approaches.
> Domain:  adef : schemas.ActivityDef ; ?now ?reset-at : integer | nil
> Returns: integer >= 1.

### `M.deficit [goal ?progress]`

> What is still missing toward the target.
> Domain:  goal : GoalDef ; ?progress : number | nil (nil reads as 0)
> Returns: number >= 0.

### `M.activity-yield [goal activity-id ?gold-bands ?custom-yields]`

> Expected per-run payout of one activity toward one goal.
> Gold uses the band midpoint (the projection keeps the full band); items pay
> their per-run drop chance (expected drops); chains never pay through
> activities -- their path is the chain advisory, not the route. Badges and
> rep read the authored override first when the activity is a custom one
> (Phase 8); custom gold rides :gold-bands, merged by ctx.build.
> Domain:  goal : GoalDef ; activity-id : keyword|string
> ?gold-bands : {activity-id {:min :max}} | nil -- blended overrides
> ?custom-yields : {activity-id ActivityYield} | nil -- authored
> custom-activity payouts (RouteContext)
> Returns: number >= 0 in the goal's own unit.

### `M.make-goal-scorer [?goals ctx]`

> Build the per-activity goal scorer route.plan-week folds into its score.
> Per goal: the week's BEST source (max yield x runs over the registry) earns
> the goal's full urgency as a score boost -- the same magnitude as one
> default-weight BiS slot -- and every other source earns its proportional
> share, so an urgent goal visibly reorders the plan toward its densest
> activities. Deficit, achievable-by-reset, urgency and best-source are
> precomputed once (over the full registry plus the player's custom entries
> -- an optimistic ceiling; lockouts shave it implicitly by shaving the
> plan); the closures are O(goals).
> Domain:  ?goals : [GoalDef] | nil -- RouteContext :goals
> ctx    : RouteContext (reads :goal-progress :gold-bands
> :custom-activities :custom-yields :now :reset-at)
> Returns: {:active?   boolean -- any goal still has a deficit
> :relevant? (fn [activity-id] -> boolean) -- pays toward some goal
> :score     (fn [activity-id] -> number >= 0)} -- the score term,
> <= urgency per goal; a no-goal scorer is inert (active? false,
> score 0), so plans without goals are byte-identical to pre-goal
> plans.

### `M.project [goals steps ctx ?opts]`

> Per-goal P10/P50/P90 projection of where the player lands by reset, given
> the planned steps -- 'P50: 130 of your 150 badges'. Deterministic kinds
> (badges, rep) are arithmetic so all three percentiles agree; gold samples
> each run uniformly inside its activity's band (seeded MC); items are the
> at-least-one Bernoulli; rep standing and chain fractions project flat (a
> plan does not advance them mechanically -- honest, not optimistic).
> Domain:  goals : [GoalDef] ; steps : route.plan-week :steps
> ctx   : RouteContext ; ?opts : {:sims ?int>0 :seed ?int}
> Returns: [{:id :kind :target number :progress number
> :p10 :p50 :p90 number} ...] -- absolute, goal units.
